# 第 2 步 · 调研(Research) — 子 agent 执行说明

## 目标
摸清"现状 + 数据能力 + 可借鉴",让第 3 步设计有据,杜绝拍脑袋和"设计出无数据支撑的占位符"。

## 输入(编排器传入)
第 1 步的 6 轴定案、主题名 `name`。

## 必读参考
- `reference/theme-api.md` —— 数据模型全字段、公开端点、模板选择规则(**核对数据可行性靠它**)。
- 项目 `CLAUDE.md`、`docs/frontend.md`。

## 步骤
1. **读目标主题现状**:`frontend_themes/<name>/` 全部 `.vue` + `theme.config.ts`。逐文件列出问题:死链接、占位符/硬编码假数据、未加载的字体、Markdown 未渲染、`@click=router.push` 式伪链接、无分页、未用 `menus` 等。
2. **核对数据可行性**(关键):把 6 轴要的**每个页面、每个字段**对着 `theme-api.md` 的数据模型过一遍——后端到底给不给?给不了的(如"阅读量/来源/发文单位")要么落到 `article.data`(并在分类 `article_data_fields` 声明),要么砍掉。**先确认数据可得,再谈 UI。**
3. **借鉴现有主题**:`pear`(极简)/`neo`(粗野·工作室)/`school`(学院官网)/`cosmos_love`(多模板)。已实现的模式(分页 composable、marked、Socials、configSchema、字体加载、Landing 自动发现)直接复用,别重造。
4. **参考真实站点**(可选但推荐):用 `WebFetch` 拆解一个**同类**真实站点的信息架构(顶栏/导航/首屏/分区/页脚),对照补齐遗漏。**从需求出发,不要从现有半成品文件出发。**
5. **激活主题以便后续开发**:`cd frontend && npm run theme:use <name>`。

## 产出(交回编排器)
- **现状问题清单**(按文件/按类别)。
- **数据可行性结论**:每个拟定页面/字段"可得 / 需入 data / 不可得需砍",附映射方案(分类约定、`article.data` 字段、`theme_<name>_*` 配置)。
- **借鉴点**:可复用的现有模式与参考站的结构启发。

## 门禁 / 交接
把上述结论交回编排器转述给用户;不要顺手进入设计文档或写代码。数据不可行的需求,在这一步就标红,供第 3 步取舍。
